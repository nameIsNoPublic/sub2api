# 工单支持与知识沉淀

## 工单闭环

用户从「我的工单」提交标题、分类和问题描述。管理员从「工单管理」按状态查看队列和回复。工单详情按时间展示发起、回复、解决、结束和重开记录。

| 当前状态 | 操作 | 新状态 |
| --- | --- | --- |
| 待客服或待用户 | 用户补充说明 | 待客服 |
| 待客服或待用户 | 管理员回复并等待补充 | 待用户 |
| 待客服或待用户 | 管理员提交解决方案 | 待确认 |
| 待确认 | 用户确认解决 | 已结束 |
| 待确认 | 用户说明原因并重开 | 待客服 |
| 待客服、待用户或待确认 | 用户或管理员结束工单，可附结束说明 | 已结束 |
| 已结束 | 用户说明原因并重开 | 待客服 |
| 已结束 | 管理员说明原因并重开 | 待用户 |

用户只能访问本人发起的工单。已结束的工单可由任一方说明原因后重新打开，重开说明作为发给对方的消息，所以由管理员重开时状态为待用户。第一版由管理员共用队列处理，在页面中查看进展。消息正文以纯文本存储和展示，可随消息上传图片。前端支持点击选择、拖拽和粘贴截图，提交前可预览、移除。

## 接口约定

用户接口以 `/api/v1/support-tickets` 为前缀，管理接口以 `/api/v1/admin/support-tickets` 为前缀，分别复用现有用户和管理员鉴权。两端的列表支持 `status`、`page`、`page_size`，详情默认加载最近一页记录，使用返回的 `next_before` 加载更早的记录。

- 用户使用 `POST /` 创建工单，请求体为 `{"subject":"请求返回 429","category":"api","body":"使用某模型时收到 429"}`，请求头带 `Idempotency-Key`。同一用户重试相同请求时返回原工单编号。分类可选 `api`、`billing`、`account`、`other`。
- 两端使用 `POST /:id/actions` 追加记录，例如 `{"action":"resolve","body":"降低并发后重试","version":3}`。用户动作包括 `reply`、`confirm`、`close`、`reopen`，管理员动作包括 `reply`、`resolve`、`close`、`reopen`。`close` 的 `body` 可为空，其余动作（`confirm` 除外）必须填写。用详情返回的 `version` 防止重复提交或基于旧状态操作。冲突返回 409，刷新详情后可以继续处理。
- 工单正文、回复和知识内容不进入请求体审计。审计记录保留操作者、路由、工单编号与结果。

## 站内提醒

不发送邮件。面板登录后每分钟请求一次 `GET /summary`，页面在后台时跳过，切回前台时补一次。用户端返回 `{"attention":1,"activity":12}`，`attention` 是有客服新进展、本人还没看过的工单数。管理端的 `attention` 是待客服的工单数。`activity` 是范围内工单版本号之和，有工单新建或任一方操作时都会变化。

- 侧边栏「我的工单」「工单管理」显示 `attention` 计数，超过 99 显示 `99+`；侧栏折叠时改为图标右上角圆点，移动端在菜单按钮上显示圆点。
- 用户列表项的 `unread` 为真时，标题加粗并带圆点。用户打开工单详情的最新一页即视为已读，加载更早记录和管理员查看不改变已读状态。用户自己的回复、确认或重开不会产生未读。
- 工单页面在 `activity` 变化时刷新列表。正在查看的工单出现更新版本时，详情自动刷新，输入框中的草稿和焦点保持不变。
- 已读位置保存在 `support_tickets.user_seen_version`（`253_support_ticket_read_state.sql`），只会前进。升级时存量工单全部视为已读。

## 图片附件

创建工单和提交回复、解决方案或重开说明时，可将原 JSON 请求改为 `multipart/form-data`。将原 JSON 放入 `payload` 字段，每张图使用一个 `images` 文件字段。例如 `-F 'payload={"subject":"请求出错","category":"api","body":"见截图"}' -F 'images=@screenshot.png'`。每条消息最多 3 张 PNG、JPEG 或 WebP 图片，每张不超过 5 MiB 和 1600 万像素。

详情事件的 `image_count` 表示图片数量，编号从 1 开始。通过工单对应的用户或管理接口 `GET /:id/events/:version/images/:position` 读取图片原始字节。图片和对应的工单记录在同一事务写入，和工单一起保存在 PostgreSQL 中，仅工单发起人及管理员可查看。图片不进入审计请求体和知识导出。

### 管理员配置

管理员在「系统设置 → 安全 → 工单图片上传与存储」调整账号/全站每分钟上传次数、单工单/账号/全站图片数量和账号/全站容量。参数保存到现有 settings 表，升级后未保存时沿用下列默认值，无需新增 Schema。

接口为 `GET /api/v1/admin/settings/support-ticket-images` 和同路径的 `PUT`。保存完整的配置对象，字段包括 `user_rpm`、`site_rpm`、`ticket_max_images`、`account_max_images`、`account_max_mib`、`site_max_images`、`site_max_mib`，均为正整数。存量配额在每次写入事务中读取最新配置，当前节点的上传频率立即刷新，其他节点最多 1 分钟内刷新。降低存量上限后历史图片继续保留，新附件按新值检查。

### 上传防滥用（默认值）

- 读取文件前按上传者账号和站点计数。每个账号每分钟最多发起 6 次图片上传请求，站点合计最多 30 次，包含无效上传和重试。多实例共用 Redis 计数，Redis 不可用时暂停图片上传。
- 每个服务进程最多处理 2 个并发上传，同一账号在同一进程内最多 1 个。每次请求体读取总时限为 60 秒。
- 每张工单最多保留 12 张图片。按工单归属账号累计，最多保留 60 张和 100 MiB。站点最多保留 10,000 张和 2 GiB 原始图片数据。客服附图也计入对应工单的存量。
- 附件额度和写入在同一数据库事务内校验。写入被拒绝时，工单状态、消息和附件一并回滚。相同创建请求的幂等重放只返回已有工单。
- 限流时返回 429 和 `Retry-After`。存量超限返回 429 和 `SUPPORT_TICKET_IMAGE_QUOTA`，`metadata.scope` 指明 `ticket`、`account` 或 `site`。可以移除本次附件后发送纯文字，历史图片继续保留。存量按仍保存在数据库里的附件计算。

## 智能客服数据入口

工单结束后，管理员可在详情中手工撰写可复用的问题和答案，审核并去除账号信息、订单号、凭证和私密日志后发布。每个工单对应一份可更新、可撤回的知识条目，工单原文始终留在工单详情。

管理端使用 `PUT /:id/knowledge` 发布或撤回。首次发布示例为 `{"published":true,"question":"收到 429 怎么办？","answer":"降低并发并按退避策略重试。","revision":0}`。更新和撤回使用详情中的知识 `revision`。

后续索引任务可读取 `GET /api/v1/admin/support-tickets/knowledge?after_id=0`。每项只含 `id`、`category`、`question`、`answer`、`revision`、`updated_at`，每次最多 100 项。以 `next_after_id` 翻页，直至游标省略。使用 `id` 作为索引键、`revision` 判断内容是否更新，并在成功完成全量扫描后清理缺失条目，以同步撤回或删除。扫描期间有更新时，由下次扫描校准。

部署时由现有迁移程序应用 `250_support_tickets.sql` 至 `254_support_ticket_close_action.sql`。本期交付工单和经审核的知识源，向量索引和机器人问答属于后续接入。
